# One continuous neighborhood Ã¢â‚¬â€ plan (decided)

User rules: ONE big seamless map (~160x120 tiles, extensible). Static things (terrain, roads, sidewalks, lots, buildings, trees) always exist and may be rendered (chunked + culled). Dynamic things (people, cars, animals, ambient crowds, simulated props) are simulated/rendered ONLY when a player Folk can perceive them (distance AND line of sight). Everything else runs on the cheap statistical sim (Away / NeighborhoodService / Story). Keep it simple: small files (<~400 lines), no god files.

## Key facts about the current code
- The sim does not step tiles: `Interaction.start()` computes `path_length` once, sets `travel_left = n * WALK_MIN_PER_TILE`, `_arrive()` teleports. Only FolkView animates the walk along `World.find_path`. So statistical and Active sim already share one logical model; long walks just mean a long travel time.
- Autonomy cost: `path_length` (full A*) per candidate; `objects_near` radius 64. Must be bounded (radius ~24, skip far candidates, cache).
- `World` is one global grid; `WorldRooms` flood-fills the whole grid when dirty Ã¢â‚¬â€ must become region-limited/lazy.
- `Neighborhood` currently swaps lots (stash/load); it becomes a registry of lots at map coordinates.

## Data model
- Keep one `World` autoload, grid 160x120. New `scripts/world/world_regions.gd`: regions {rect, kind(home|venue|townie_home|park|road), venue_type, owner, template, entry, label}; `region_at(tile)`; `can_build(tile)` true only in the player's lot (hook into place/edit/buy).
- Chunks 16x16 are an index only (`chunk_of`, chunk -> object ids), not storage.
- `LotLoader.apply(template, origin)` places all templates once at map build using origins from data/neighborhood.json (translate wall edges, objects, spawn/entry/bedroom/staff).
- Static = floors/roads/walls/fences/trees; Dynamic = objects with state, Folk, vehicles, animals. Objects stay WorldObjects (data), only node instancing is gated by activity.
- Save version bump; old saves dropped. One world dict + regions; Neighborhood saves pantry/visits/meetups only.

## Pathfinding
- New `world_nav.gd`: portal graph (lot entry tiles + road/sidewalk junctions, edge weight = tile distance). find_path: same region/near (<32 tiles) -> bounded-window tile A*; else A* to entry portal + graph route + A* from entry portal. Cache portal routes by region pair and path_length by tile pair (LRU ~256), invalidate on wall/object changes. path_length across regions may return cached portal distance (exact path only needed in Interaction.start()).
- Autonomy: skip candidates > ~40 tiles (Manhattan); `objects_near` radius 24; far errands (market/cafe) chosen by a venue-level scheduler.

## Interest / LOD (`scripts/sim/interest.gd`, class Interest)
- Tiers: ACTIVE (full sim + render), NEAR (full sim, no render, autonomy every 3rd tick), FAR (statistical: existing sys_away stay).
- API: is_active(tile), tier_of(folk), refresh() once per game minute, active_rects(), active_chunks().
- Area per player Folk: indoors = current room + rooms through doorways + windows/doors visibility; outdoors = radius ~24 with LOS blocked by wall edges (bounded flood fill / ray test, windows transparent for LOS, buildings opaque from outside). Cached, recomputed on tile step or wall change.
- Transitions: FAR->ACTIVE places the folk at a plausible tile (along cached route at elapsed fraction, or free slot at their venue); ACTIVE->FAR only if out of view > ~10 min (hysteresis ~5). Crowd/staff per venue region, spawned only when region ACTIVE/NEAR. Director ticks ACTIVE every tick, NEAR every 3rd, hard cap ~12 autonomy folk per tick.

## Rendering
- Per-chunk floor meshes (re-mesh on floors_changed per chunk); road/sidewalk floor types. Walls per chunk, nodes only for Active chunks +1 margin; merged static mesh per far building. Objects instanced only in Active chunks. Interior detail + cutaway only for buildings containing/adjacent to a player Folk. Camera follows selected Folk, free pan clamped to map. Dim chunks outside Active set (simple). Budget < 2k draw calls.

## Ambient life (after tiers)
- Pedestrians: lightweight visual-only entities spawned at the edge of the Active bitmask, walk the sidewalk graph, despawn leaving it. Cars: position along lane polylines, no physics, capped (~6 per 100 road tiles in Active). Animals: 0-3 in Active parks. Blender: car x2, trees, road pieces, fence, mailbox, streetlamp, bush, house shells/roofs.

## Gameplay integration
- Travel panel becomes a map overview; "Go" sends the Folk walking (goto_tile) to the lot entry; optional fast-travel = Away travel time. Venues' check_entry/charge_entry run at the door. Work/school rabbit-hole stays. Story visitors spawn at the home entry/map edge. Start picker places the chosen home template at the player's origin on a pre-made map.

## Phases (each leaves the game playable)
P1 big grid + static render + clamped camera (world.gd size, world_save, world_rooms region-limited, lot camera/chunk meshes, world_regions). 
P2 lots placed on the map (LotLoader origin, Neighborhood registry-only with thin wrappers, neighborhood.json origins, Economy owner per object, per-chunk walls).
P3 hierarchical pathing + walking between lots (world_nav, world_paths bounded/cached, world_iface, autonomy radius, interaction, folk_motion segmented, travel panel).
P4 interest tiers (interest.gd, director tier lists, away materialize, crowd/neighborhood_service per region, instance gating).
P5 ambient life (ambient_ped/car/view + Blender assets).
P6 map overview UI, minimap, saves, start picker changes.
Parallel: P1 + Blender assets; P2 || P3 after P1 once WorldRegions/WorldNav interfaces are fixed; P4 after P2/P3; P5 after P4; P6 after P2.

## Fallbacks
Rooms cost -> per-lot lazy rooms. A* cost -> distance-only beyond 24 tiles. LOS cost -> distance + room-based interest. Wall node count -> merged mesh per building. Fog -> chunk visibility only. Neighborhood rewrite breakage -> keep old API as wrappers.

## Not building
Per-chunk storage streaming, physics vehicles, per-tile fog-of-war textures, full visual sim of FAR folk, save diffs, navmesh. (Multi-floor buildings: see "Multi-floor: decisions" below.)

## P3 status / decisions (done)
- **Routing** (`scripts/world/world_nav.gd` `WorldNav` = `World.nav`, `nav_graph.gd` `NavGraph`, `nav_field.gd` `NavField`, `lru_cache.gd`): `World.find_path / path_length / has_path` go through it (plain `WorldPaths` A* for worlds <= 4096 tiles / without regions / `WorldNav.enabled = false`). Same lot or same park = A* restricted to that rect (`WorldPaths.find_path_rect`, wall-edge aware, never leaves it, fails after <= rect-area expansions). Otherwise: exit leg (lot tile -> the lot's gate `region.entry` -> the sidewalk tile south of it; open ground / road / park -> nearest sidewalk found by 4 rays <= 40 tiles + bounded A*), route over the ribbon graph, entry leg (= the destination's exit leg reversed, so legs are cached once per tile). The graph is generated from data/map_layout.json: nodes = run end points, runs = straight sidewalk stretches, 1-step corner links and crosswalks (the only runs that join two sides of a road; ~240 nodes), Dijkstra per source node cached; a run is blocked by any blocking object / wall edge on it. Route length == tile count == what `path_length` returns (path_length never builds the tile list). Caches (LRU legs 1024, lengths 4096, routes 1024, fields 8) are dropped by `nav.touch_tile / touch_edge` (hooks in `WorldObjects` place / remove, `WorldEdit.set_edge`, `World.reset`); the graph is only re-validated when the change touches a ribbon tile. A `NavField` (one Dijkstra over the lot, identical step counts to A*) is built after 3 in-lot `path_length` questions from the same tile (autonomy scores ~100 candidates from one tile).
- **Unreachable fails fast** (< 1 ms): fenced / blocked gate -> `_exit` returns null; blocked sidewalk run -> `plan` is empty (route goes round the block or is unreachable); walled-in tile -> bounded rect A*. No whole-map search any more for map paths.
- **Walking**: `Interaction.start` computes the route ONCE (`path`, trip time = steps x `WALK_MIN_PER_TILE`, now 0.3 min: home -> cafe door 89 tiles = 27 min, a neighbouring lot ~10 min; 0.5 made the cafe a 45 min trip). FolkView no longer plans anything for long walks: `_route_slice` takes the part of `f.current.path` between the last and the current tile (jumps > 24 tiles = fast forward / fast travel teleport the view). `BASE_SPEED` unchanged (2.4): at speed 1 the sim walks 3.3 tiles/s, the view speeds up by its waypoint backlog and shows 'Run' while it catches up.

Trips cut short (`Interaction.finish(false)` with reason preempted / interrupted on a `go_here` tagged with a lot) set meta `resume_walk [lot, minute]`; `on_minute` re-issues the walk (queued behind the more urgent thing); older than 180 min (`RESUME_MAX_MIN`) -> dropped with a "gave up on going to" toast.

## Commutes: decisions (task 11, done)
- **Leave time** = shift start - (path_length x `WALK_MIN_PER_TILE` / (`Health.speed_mult` x `Weather.walk_speed_mult_at`) + 10 min buffer); evaluated each minute only within 4 h of the start (path_length is LRU cached). The walk is one `go_here` (priority high so it preempts the sofa, never a player command) tagged `params.commute`; a cut walk is re-issued when the folk is free, a player command on the way = missed shift, nothing by `miss_after_min` (90) = missed shift (`missed_shift`).
- **Late** = arrival minute - shift start > 5 min grace: -1.5 performance per started 10 min (max 10) / -1.5 grade for school, toast + `late_for_work`; weather and injury are in the plan, so lateness comes from a late departure (clock jumps, loading mid-lead), interruptions and unplanned traffic (`Traffic.provider` crossings add `delay_min` to the real walk but not to the plan).
- **Inside**: on arrival the folk is moved to a desk of the lot (or the staff post, or the door) and `Away.send(..., data.commute)`; `restored_start = max(arrival, shift start)` keeps pay identical to the old rabbit hole. Visible careers use `Away.begin_visible` (a record without the hiding interaction) and `VisibleWork.step` each minute.
- **Townies**: `CommuteTownies.window` (workday, shift hours, per-townie arrival offset) is the statistical truth (`lot_now(tid)`); the crowd only materialises them for a near lot. Townies on shift never fill the crowd of another lot.
- **Rough edges**: a late/missed trip does not wait at crosswalks or flip to a bus/car (no vehicles yet); the multi-floor hook is `Workplace.entry_tile(career).level` (always 0 now); a visible worker is freed from autonomy for the whole shift (needs drift like the rabbit hole); the "chat at the door" is a friendship bonus, not a real `chat` interaction.

## Multi-floor: decisions (task 10 part A)
- **Additive, not a rewrite.** `level: int` sits NEXT TO the tile (Folk, WorldObject, Interaction.goto_level) and defaults to 0; level 0 stays in the World's own grid, upper and lower levels are sparse `LevelLayer`s (one per level number, global, buildings never overlap) with building records (rect + level range) in `World.levels`. Every old call keeps working unchanged; level-aware overloads take a trailing `level` argument.
- **Position type**: `Vector3i(x, y, level)` (`LPos` helpers), routes are `Array[Vector3i]`. Folk and objects keep a `Vector2i` tile plus an `int` level (a Vector3i inside them would have been a risky migration).
- **Between floors = portals**: ground nav (WorldNav) + per-level tile A* (LevelPaths) joined by a lazy portal-graph A* (LevelRouter). Stairs 2x1, ladders 1x1, lifts (one object, `span`, capacity, out of order), fire escapes (outside stairs). Vertical travel is part of every distance (autonomy); stairs cost more for elders, toddlers and the injured.
- **Structure rules are simple and explainable**: a floor needs a wall or pillar of the level below within 4 tiles; you cannot remove what a floor rests on; a level can only be added while a staircase, ladder or lift reaches it; each level costs more than the last.
- **Rendering**: only the ACTIVE building draws its other levels (merged meshes per level, objects of the viewed level only); far buildings are one shell scaled to their height. Floors above the viewed one are not drawn; the basement view hides the ground inside the building.
- **Budgets met** (15-storey tower on the full map): cached route length ~0.002 ms, uncached cross-level about 1 ms average with a warm street graph (5 ms worst, the first call), stairs-only 14-flight climb 3.5 ms; a 20-floor tower is 74 KB of save.
- **Left for part B**: generators (hospital, tower, apartments, courthouse, police cells, parking garage, school, houses with 1-3 floors + basement), fire / accident / disaster / crime hooks by level, hospital births, shelters in basements, per-level light / noise / decor mood.

## Multi-floor: decisions (task 10 part B)
- **One generator, one frame.** Every multi-floor building is a corridor with a stair core between two bands of cells (`BldgFrame` abstracts axis and mirroring: `u` along the corridor, `v` across), so stairs, lift and entry are always in the same relative place on every floor, floors read the same way (the player learns one layout), and the generator reuses the home furnishing engine per level instead of a second one. Stairs are switchbacks (even levels climb one way, odd levels the other, a free walkway beside them) so any number of floors and a basement fit the same 4x3 core; a lift adds one column.
- **Buildings live in their own file** (`data/generated_buildings.json`, `tools/gen_buildings.gd`), merged by `LotLoader`, so the single-storey generated set and its tests (fixed footprints) are untouched; floored homes join the home pools by id prefix (`medium_f01`, `large_f02`...).
